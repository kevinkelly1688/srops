# StarRocks 运维平台 · POC 测试用例

| 项目 | 内容 |
|---|---|
| 平台版本 | v0.10.0（以「平台设置 → 基础」或 `GET /api/health` 返回为准） |
| 文档用途 | 在客户 / 内部的**真实测试集群**上验证平台能否满足运维需求，形成可签字的 POC 结论 |
| 适用对象 | 实施工程师、DBA、运维负责人、安全与审计人员 |
| 配套文档 | 《用户使用手册》（功能说明）、`backend/README.md`（部署与参数） |

---

## 1. 目标与范围

**目标**：用一套真实的 StarRocks 测试集群，回答三个问题：

1. 平台**能不能安全地接入并管理**集群（接入、权限、审计、密码保护）；
2. 日常运维**能不能替代**手工操作（监控、巡检、查询分析、参数、节点、备份、告警）；
3. 高风险运维（**部署、扩容、升级、回滚**）**是否可靠**，失败后能否恢复。

**范围**：平台全部 18 个页面。**不在范围内**：HDFS / Azure 仓库的快照清理（仅支持 S3 协议存储）、告警规则分组与自定义通知模板（平台暂未提供）。

> ⚠ 重要提示：平台自带的假集群（`fakesr`）只能验证流程与命令顺序，**不能代替真实验证**。第 3 部分的“高危用例”（节点启停、扩容、部署、升级、回滚）必须在真实测试集群上执行，**严禁**在生产集群上做 POC。

## 2. 测试环境

### 2.1 平台服务器

| 项 | 要求 |
|---|---|
| 系统 | Linux x86_64 / aarch64（与安装包一致），能访问 FE 的 query_port / http_port，以及各节点的 SSH 端口 |
| 资源 | 2C 4G 以上，数据目录 10 GB 以上 |
| 部署 | `sr-ops-<版本>-linux-<架构>.tar.gz`，按手册「平台部署与集群导入」安装；对外访问放在 HTTPS 反向代理之后（`-trusted-proxies` 配置代理地址） |
| 初始账号 | `admin`，初始密码见 `data/initial_admin_password`，首次登录强制改密 |

### 2.2 StarRocks 测试集群（建议）

| 项 | 建议 |
|---|---|
| 版本 | 3.3 ~ 3.5（升级用例需要比当前版本高一个小版本，且官方包可下载；例如当前 3.4.x → 目标 3.5.x） |
| 拓扑 | **FE 3（1 Leader + 2 Follower）+ BE 3**；存算分离另备 CN 若干。至少 1 台**空白主机**用于部署 / 扩容用例，再多 2 台更好 |
| 数据 | 至少 1 个库 5 张以上表，含 1 张 Primary Key 表、1 个物化视图、1 个 Routine Load；总数据量 ≥ 10 GB，便于观察升级期间 Tablet 恢复 |
| 账号 | 运维账号（建议 `sr_ops`），按手册授予 `SHOW` / 系统查询所需权限；查询审计用例需要安装 AuditLoader |
| 主机 | 专用 SSH 用户（有免密 sudo，或使用 root），所有节点使用**同一 SSH 用户与端口** |
| 可选 | Prometheus（趋势图与指标类告警）、SMTP 邮箱、企业微信 / 钉钉 / 飞书机器人（通知用例）、S3 / OSS / MinIO 仓库（备份用例） |

### 2.3 测试账号

在「用户管理」中建立下表账号，用于权限与复核用例（密码任意，满足策略即可）：

| 账号 | 角色 | 数据范围 | 用途 |
|---|---|---|---|
| `poc_admin` | 超级管理员 | 全部 | 配置与全量验证 |

| `poc_audit` | 审计员 | 全部 | 审计与合规验证 |

### 2.4 备份数据（回退保障）

POC 开始前确认：测试集群有可用的元数据备份（FE `meta` 目录）；重要表已做备份；记录各节点当前版本、配置文件快照，便于升级 / 回滚用例失败后还原。

按**风险从低到高**执行，前一组不通过时先处理，不要直接做高危用例。

| 3 | G 参数配置 | 5 | 中 | **是** |
| 3 | H 备份恢复与快照清理 | 9 | 中 / 高 | **是**（需 S3 仓库） |
| 3 | I 告警中心 | 10 | 中 | **是**（短信用例需短信账号或网关） |

## 4. 通过标准

| 等级 | 标准 |
|---|---|
| **通过** | 所有 **P0** 用例通过，P1 用例通过率 ≥ 90%，无未处理的数据丢失 / 越权 / 密码泄露类缺陷 |
| **有条件通过** | P0 全部通过，P1 通过率 80% ~ 90%，遗留问题有明确的规避方案与修复计划 |
| **不通过** | 任一 P0 失败；或出现越权、凭据泄露、集群数据受损 |

优先级：**P0** = 核心 / 安全 / 高危操作；**P1** = 重要功能；**P2** = 辅助功能。结果栏用 ✅ 通过、❌ 失败、⚠ 部分通过、➖ 未执行。

### I. 告警中心

## 6. 风险与回退

| 风险 | 缓解 / 回退 |
|---|---|
| 节点停止 / 重启造成查询失败 | 只在测试集群、业务低谷执行；FE ≥ 3 台；L-04 之前确认 Follower 存活 |
| 升级失败或元数据不兼容 | 升级前备份 `meta`；升级器会自动保留 `bin.bak-<版本>` / `lib.bak-<版本>` / `meta.bak-<版本>`；使用平台“回滚”，必要时手工替换目录并启动；不要在升级后使用新版本特性再降级 |
| 部署误覆盖已有目录 | 仅使用空白主机；部署会清空并重建目标安装目录，务必确认目录为空或可丢弃；先预检再部署 |
| 备份目录与安装包占用磁盘 | POC 结束后手工清理 `*.bak-*`、`.upload` 目录；旧快照可用保留策略清理（仅 S3 仓库，且只在测试仓库验证后再用于正式仓库） |
| 凭据与审计合规 | POC 账号用完即删；POC 结束后在平台删除测试集群，导出审计日志留档 |
| 平台自身故障 | 平台只做运维编排，不在查询路径上；平台宕机不影响 StarRocks 集群运行 |

## 7. 已知限制（评估时请纳入考量）

- 部署只支持官方默认端口；所有部署主机必须使用同一组 SSH 用户与端口；同一台主机同类型节点只支持一个。
- 升级只替换 `bin`、`lib`（FE 还有 `spark-dpp`），不修改 `conf/`；新版本新增的必须配置需手工处理。
- 升级留下的备份目录、上传到主机的安装包不会自动清理；备份快照仅在设置了保留策略的 S3 仓库中自动清理，且删除不可恢复。
- 自定义 PromQL 规则只支持即时向量查询，不支持规则分组与自定义通知模板；短信按条计费，请只让“严重”级别发短信。
- 平台自带假集群只验证流程，真实升级 / 回滚的耗时与脚本差异以真实集群为准。
