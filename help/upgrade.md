# 升级回滚

## 1. 升级原则（官方）

- **升级顺序**：先 BE → 再 CN → 最后 FE；FE 内部按 Observer → Follower → Leader。
- **降级 / 回滚顺序相反**：先 FE（Leader 最后），再 CN / BE。
- **逐级升级**：同一大版本内不能跨小版本（3.3 → 3.5 须先升到 3.4）；补丁版本之间可以直接升级。
- **降级的限制**：降级前不能使用新版本才有的特性，否则新特性产生的元数据 / 数据旧版本无法识别。

> 升级需要 SSH 与部署目录（集群「待完善」时不可用），并且目标版本的安装包已在「安装部署 → 安装包」上传。

## 2. 创建升级计划

点击 **＋ 创建升级计划**（`upgrade.create`）：

- **目标版本**：来自已上传的 StarRocks 安装包（当前版本之外）。平台校验升级路径：低于当前版本的不能选（降级请用“回滚”），同一大版本内跨小版本会被拒绝并提示先升级到哪个版本。
- **每台间隔**：每个节点升级完成且 Tablet 健康后再等待的秒数（默认 60）。
- **暂停 Tablet 均衡**：勾选后，平台在升级期间设置 `tablet_sched_disable_balance = true`，结束后恢复原值。

计划的状态：待执行 → 升级中 / 已暂停 → 已完成；失败后可继续；回滚中 / 已回滚。没有执行过的计划可以删除。

## 3. 升级前检查

选中计划后点击 **升级前检查**（执行升级时平台也会自动检查，**存在“不通过”项会拒绝开始**）：

| 检查项 | 不满足时 |
|---|---|
| FE / BE / CN 全部存活 | 不通过 |
| 不健康 Tablet = 0 | 警告（升级过程中还会逐台等待 Tablet 恢复） |
| FE 高可用（Leader + Follower ≥ 3） | 警告（单 FE 升级时有短暂不可用） |
| 目标版本安装包已上传 | 不通过 |
| 升级路径合法 | 不通过 |
| 所有节点主机 SSH 可登录 | 不通过 |
| 安装目录存在（`bin`、`lib`） | 不通过 |
| CPU 架构与安装包一致 | 不通过 |
| 安装目录所在磁盘有足够空间 | 不足 2 GB 不通过，不足 10 GB 警告 |
| 没有进行中的备份 / 恢复作业 | 警告 |
| Tablet 均衡、FE 元数据备份 | 提示 |

## 4. 执行滚动升级

点击 **▶ 执行**（`upgrade.execute`，高危，可走双人复核）。服务端按升级顺序**逐台**处理，每个节点：

1. 上传安装包到节点主机（校验 SHA256；已有同样文件则跳过），解压到临时目录；
2. **优雅停止**进程（BE / CN 3.4 及以上带 `-g`），确认进程已退出；
3. **FE 还会先备份元数据**：把 `meta_dir` 复制为 `meta.bak-<旧版本>`；
4. 把 `bin`、`lib`（FE 还有 `spark-dpp`）**改名为** `<目录>.bak-<旧版本>`，再从安装包复制新版本的目录。`conf/`、日志和数据目录**保持不变**；
5. 启动进程，等待节点存活，并且 `SHOW` 里显示的版本等于目标版本；
6. BE / CN 之后再等待“不健康 Tablet = 0”（最长 10 分钟，超时则**停止升级**以免影响数据可用性）；
7. 按“每台间隔”等待，处理下一台。

页面每 3 秒自动刷新，列表实时显示每个节点“待升级 / 升级中… / 已是新版本”；点击 **查看日志** 看每条命令。已经是目标版本的节点会被跳过，所以升级可以**中断后继续**。

- **暂停 / 继续**（`upgrade.pause`）：暂停在**当前节点完成之后**生效，不会在节点中途停下；继续后接着处理下一个节点。
- **取消**（执行中出现的 **取消** 按钮，需要 `upgrade.execute` 权限并输入集群名确认）：同样在当前节点完成后停止，计划标记为失败（备注“已取消”），可再次 **继续执行**。
- 升级失败（例如某节点没能以新版本存活）：计划标记为失败，备注失败原因；处理后点击 **继续执行**，或 **回滚**。
- 升级全部完成后，平台恢复 Tablet 均衡，并把集群版本更新为目标版本。

> 暂停均衡是 FE 的**内存配置**：FE 重启后会恢复默认值，所以只有 BE / CN 阶段是确定被暂停的；平台在结束时仍会再设置一次恢复值。

## 5. 回滚

**回滚 / 降级**（`upgrade.rollback`，高危，可走双人复核）把已升级的节点恢复成升级前的版本，顺序为 **FE（Follower → Observer → Leader 最后）→ CN → BE**：

1. 优雅停止；
2. 删除当前的 `bin`、`lib`，把升级时改名的 `*.bak-<旧版本>` 目录**改回原名**；
3. 启动并等待以旧版本存活。

如果某个节点上的备份目录已被清理，平台会尝试用「安装包」里的**旧版本安装包**重新安装 `bin / lib`；两者都没有则该节点回滚失败，并说明原因。回滚期间 Tablet 不健康只给出警告、不会中止（回滚是应急操作）。

> ⚠ 回滚前请确认没有使用过新版本的新特性，否则旧版本可能无法识别新产生的元数据 / 数据。**建议升级完成并稳定运行一段时间（≥ 1 天）后，再开始使用新版本特性、清理备份目录。**

## 6. 升级后的清理

平台**不会自动删除**这些目录，确认升级稳定后请手工清理以释放空间：

- 每个节点的 `bin.bak-<旧版本>`、`lib.bak-<旧版本>`（FE 还有 `spark-dpp.bak-<旧版本>`、`meta.bak-<旧版本>`）；
- 节点主机上的安装包 `<部署目录上级>/.upload/StarRocks-*.tar.gz`。

删除备份目录后，该计划就不能再回滚。
